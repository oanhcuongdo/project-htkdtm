# Recommendation rankers

## Shared candidate filter

Build one `CandidateFilterResult` from the full catalog and learner constraints,
then pass that exact result to each ranker using `candidate_filter_result`.
M0, M1, and M2 use its ordered eligible IDs and cannot add candidates outside
that result. M1 and M2 verify the filter's dataset version; M0's offline
evaluator creates the result for its requested version. The result carries the
candidate hash. M0's evaluator also records warnings and rejection reasons.

`filter_candidates()` enforces approved status, allowed offer types, exclusions
for already-purchased/already-studied courses, budget/currency, required weekly
hours, and `CoursePrerequisites`. The prerequisite mapping is
`course_id -> prerequisite_course_ids`: an empty list means verified no
prerequisites, while a missing mapping or `null` is unknown and fails closed.
Courses with unmet prerequisites, or known prerequisites but missing completion
history, are excluded. This is the safety exception to fail-open handling of
missing optional learner fields.

If a learner omits an optional filter field, that individual filter is skipped
and its field path appears in `missing_fields_warning`. If a learner supplies a
budget or weekly-hours limit but a course lacks the corresponding price/currency
or `required_hours_per_week`, that course is excluded and flagged; an unknown
value is never treated as affordable or within the time budget. Unknown
approval status is also excluded.

Cold-start fallback and the `fallback_candidates` pool are created only from
eligible courses, sorted by popularity descending and then `course_id`.
`no_eligible_candidates` returns an empty result; fallback never relaxes a hard
filter.

`LearnerProfile.candidate_course_ids` may further narrow the shared filtered
set; it cannot reintroduce a rejected course. Without a `CandidateFilterResult`,
the rankers retain their low-level behavior and treat supplied candidate IDs as
already filtered. Production callers should always provide the shared result.

The current ranker input deliberately excludes price and commission. They are
not ranking features and cannot increase an M2 score. Popularity is used only
when no usable M2 component exists for any candidate; it is not part of the M2
formula.

## Source-grounded explanations and durable traces

`explanation_builder.py` converts M0/M1/M2 outputs into a deterministic trace.
Use `ranked_items_from_m0()`, `ranked_items_from_m1()`, or
`ranked_items_from_m2()` to preserve each ranker's exact rank, score scale,
ranking method, and score components. Then call `build_recommendation_trace()`
with that result and the exact `CandidateFilterResult` used for ranking.

The filter result captures immutable copies of the learner constraints and
course prerequisites, preventing a later profile or prerequisite lookup from
changing the explanation. Skill-gap claims require target-skill IDs, learner
skill IDs, and course skill IDs; level claims require both levels; prerequisite
claims require verified prerequisite and completion data. Price and time claims
include their source values and only report budget/time fit when both sides are
known. Missing source paths are returned as `missing_fields_to_confirm`.
Explanations are templates from structured data, not generated by an LLM.

The trace includes the model/data versions, model configuration, candidate
filter decisions/hash, profile input snapshot, ranked score details, and a
course snapshot per returned item. For online use, pass the resulting JSON
payload to the backend `POST /api/v1/recommendations/runs` endpoint with
`X-Internal-API-Key`. The backend stores it transactionally in
`RecommendationRuns` and `RecommendationItems`; repeated identical request IDs
are idempotent and changed evidence under an existing request ID is rejected.
No online ranking orchestrator currently calls this persistence endpoint.

## M1 semantic embedding

M1 encodes the shared M0 `CourseDocument.text` and learner query with
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, pinned to
revision `e8f8c211226b894fcb81acc59f3b34ba3efd5f42`. The returned model version
includes both model ID and immutable revision. Cosine similarity is mapped from
`[-1, 1]` to `[0, 1]`; it is not a probability.

Call `precompute_catalog()` when publishing a dataset version to cache course
embeddings before serving requests. Compressed JSON cache files default to
`%USERPROFILE%\.cache\smartedu\m1`; set `AI_M1_CACHE_DIR` to override. Cache
keys include the dataset version, model revision, and cache schema. A content
hash rejects a changed catalog under an already-published version.

The ranker receives the shared `CandidateFilterResult` and an optional narrower
`LearnerProfile.candidate_course_ids`. An empty query uses only the filtered
popularity fallback and returns a null semantic score. Tests inject a fake
encoder so the lightweight test environment does not need the large model
dependencies.

## M2 hybrid and prerequisite roadmap

`M2HybridRanker` uses the required score when components are known:

`Score = 100 × (0.50 × S + 0.35 × G + 0.15 × L)`

- `S` is M1 cosine mapped to `[0, 1]`.
- `G` is the total target-skill weight covered by a course, divided by the
  total weight of target skills not already held by the learner. A known empty
  skill list is distinct from unknown (`null`) skill metadata.
- `L` is level proximity across `BEGINNER`, `INTERMEDIATE`, and `ADVANCED`;
  exact match is `1`, one level apart is `0.5`, and two levels apart is `0`.
  `ALL_LEVELS` is `1`. Unknown levels remain `null`.

The result records each component, its effective weight, completeness, model
version, and a 0–100 score. If a positive-weight component is unknown for a
candidate, remaining known weights are normalized and the result is marked
partial; unknowns are never silently converted to zero. If all components are
unknown, score is `null` and candidates use the deterministic popularity
fallback. The default weights are `0.50/0.35/0.15`.

`tune_m2_weights_on_dev()` evaluates supplied weight candidates using only a
split explicitly named `dev`; it rejects `test` and other split names. Use the
selected configuration for final test reporting, without further tuning.
Synthetic/unit-test labels verify mechanics only and must not be reported as
model-quality evidence.

`build_skill_roadmap()` takes target skill IDs, completed skill IDs, and
`skill_id -> prerequisite_skill_ids`. It returns a stable topological order,
omits completed prerequisites, and raises explicit errors for unknown graph
nodes, unknown prerequisite data, or cycles. The taxonomy and prerequisite
mapping must come from an approved, versioned source; the ranker does not invent
or infer that graph.

## Fair offline evaluation

`run_model_evaluation.py` runs the M0/M1/M2 comparison on exactly the `test`
learners, computes macro `NDCG@5`, `Precision@5`, prerequisite violations, and
profiles with fewer than five results, then benchmarks each model after
warmup. The benchmark requires at least 100 measured calls and a catalog of at
least 250 courses (approximately 300); M1 course embeddings are precomputed
before timing. It also reports M2 ablations with `G` and `L` removed. Ablation
weights are renormalized across the remaining components.

The JSON input contract is intentionally explicit:

- The course catalog is an array, or an object containing a `courses` array.
  Every course must provide `approval_status` and
  `prerequisite_course_ids`; course skill IDs and level must use the approved
  taxonomy and may be `null`.
- The ground-truth object uses `schema_version: 1`,
  `split_strategy: "group_by_learner"`, and `profiles`. Each learner appears
  exactly once, with `split` set to `dev` or `test`; each profile includes a
  `relevance` object mapping judged course IDs to integer grades `0`, `1`, or
  `2`. M2 data (`target_skills`, `current_skill_ids`, and
  `skill_prerequisites`) is explicit and is never inferred from free text.
- Unjudged pairs are treated as non-relevant for ranking metrics. The report
  records judgment coverage and the number of positive labels removed by hard
  filters so sparse judgments are visible.

Example (paths and versions must identify approved, immutable inputs):

```powershell
python -m src.recommendations.run_model_evaluation `
  --courses path\to\approved-courses.json `
  --ground-truth path\to\mai-ground-truth.json `
  --dataset-version DATASET_VERSION_ID `
  --output-dir reports\recommendations `
  --tune-m2-on-dev
```

The optional tuning flag uses only `dev` labels; final metrics and ablations use
only `test`. Without it, the prescribed `0.50/0.35/0.15` weights are retained.
The runner writes JSON and Markdown reports. P95 measures the in-process shared
hard-filter plus rank call; it does not include HTTP/database time because an
online recommendation orchestrator is not yet connected. To persist the same batch to
`ModelEvaluations`, set `AI_EVALUATION_API_URL` to
`/api/v1/recommendations/evaluations` and `AI_INTERNAL_API_KEY` to the backend's
internal key. The endpoint stores one row per model/ablation, with versions,
metrics, threshold outcomes, latency samples, data hashes, and run metadata.
Apply the backend Alembic migration before posting results.

No experiment outcome is asserted without the reviewed Ground Truth. The
repository's current internal demo catalog has only five courses, marked
`needs_review`, and no Mai ground-truth labels; the runner correctly refuses it
as evidence for the requested benchmark. Real target status therefore remains
unmeasured until the approved ~300-course catalog and learner-disjoint labels
are supplied.
